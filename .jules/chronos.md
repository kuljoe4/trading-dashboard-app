## 2026-06-22 - Non-Atomic SL Ratcheting Race & Protection Gaps
**Learning:** The engine's hot-loop can trigger multiple SL milestones for the same trade within milliseconds. Without a per-symbol mutex, these calls race to cancel and replace the exchange-side Stop Loss. Because Binance does not support `modifyOrder` for `STOP_MARKET`, a failed replacement after cancellation leaves the position completely unprotected. Assumed-success local state updates (updating SL price before exchange confirmation) further exacerbate this by creating a "ghost" protection level that doesn't exist.
**Action:** Always implement a per-symbol mutex for exchange-side mutations. Apply the "Acknowledge-then-Update" pattern where local state is only committed after the exchange confirms success. Mandatory "Rollback-on-Failure" must be implemented for all cancel-replace patterns to ensure capital safety.

## 2026-06-25 - Real-time Quantity Synchronization Gap
**Learning:** The engine assumed entry quantities were atomic and static. In reality, Binance FAPI User Data Stream (UDS) events often report cumulative fills (order.z) or account-level net position changes (pos.pa) that diverge from the locally tracked trade.qty during partial fills or manual reductions.
**Action:** Implemented event-driven quantity synchronization. Both ORDER_TRADE_UPDATE and ACCOUNT_UPDATE now emit a trade.quantity_sync event, triggering immediate risk recalculation and reactive watchdog audits to ensure SL protection matches the real exchange quantity.

## 2026-06-27 - Watchdog Quantity Parity Gap
**Learning:** The protection watchdog previously only verified the *existence* of a Stop Loss order, but ignored its *quantity*. Manual position adjustments on the exchange (outside the engine) or previous partial fill artifacts could leave a position significantly under-protected or over-protected (creating reverse position risk). Synchronizing the local trade quantity with the exchange position is insufficient if the associated SL order is not also synchronized.
**Action:** The watchdog must perform a "Quantity Parity Audit" on matching SL orders. Any mismatch between the order quantity and the current position quantity (excluding quantity-agnostic 'Close Position' orders) must trigger a Cancel-Replace cycle to ensure safety.

## 2026-06-29 - Non-Atomic SL Milestone Commitment
**Learning:** `PositionTrackerService` was committing R:R milestone indices to local state *before* successful exchange confirmation. If a ratchet failed (e.g. due to Binance 429 or network timeout), the engine would assume the milestone was reached and never retry the SL update, leaving the position unprotected or at a stale price level.
**Action:** Implemented the "Acknowledge-then-Commit" pattern for SL ratchets. Local milestone state and peak R:R are only updated after `OrderManagerService.updateStopLoss` returns a confirmed success from the exchange.

## 2026-06-29 - Orphan SL Order Accumulation
**Learning:** While the engine tracked its primary SL order, previous failed ratchets or external exchange activity could leave "orphan" SL orders active. Binance's limit of 10 conditional orders per symbol (Error -2027) meant these orphans could block critical protection updates.
**Action:** Enhanced the `MaintenanceService` watchdog to perform a "Single-Truth SL Audit". Any stop-loss order found on the exchange that is not the tracked `binance_stop_order_id` or matching the engine's deterministic `clientOrderId` is now explicitly cancelled.

## 2026-07-03 - Multi-Part SL Fill Data Integrity
**Learning:** During partial fills of a Stop Loss order, the local engine's `trade.qty` can diverge from the actual exchange position if not synchronized on `PARTIALLY_FILLED` events. Furthermore, if `trade.qty` is left at the remaining quantity when the final `FILLED` event arrives, subsequent PnL calculations for the closed trade will be calculated only on the final slice, leading to massive data corruption.
**Action:** Synchronize `trade.qty` with the remaining exchange quantity (`order.q - order.z`) on every `PARTIALLY_FILLED` update. Upon the final `FILLED` event, restore `trade.qty` to the total order size (`order.q`) before emitting the closure event to ensure authoritative PnL calculation across the full position.
## 2026-07-02 - Multi-Part Execution PnL & Commission Integrity
**Learning:** The engine previously ignored `PARTIALLY_FILLED` UDS events for Stop Loss orders and lacked execution-level deduplication for commissions. This led to "ghost positions" (local qty > exchange qty) during SL slippage/partial fills and double-counting of fees when the same trade was reported via both REST responses and the User Data Stream. Binance FAPI provides a unique trade ID (`t` or `tradeId`) for every execution slice which must be the authoritative key for financial state mutation.
**Action:** Implemented a `tradeExecutionCache` to deduplicate commissions by Binance Trade ID. `OrderManagerService` now synchronizes `trade.qty` to the remaining exchange quantity on SL partial fills and restores it to total order size on the final fill to ensure atomic PnL integrity.
## 2026-07-01 - Multi-Part Execution PnL Integrity
**Learning:** Exit orders (SL/TP/Manual) are not always atomic on Binance. A `PARTIALLY_FILLED` event reduces the local `trade.qty` as the engine syncs to the remaining exchange quantity. If the final `FILLED` event is processed with this reduced quantity, the PnL calculation (based on `trade.qty`) only accounts for the last slice, causing significant data-integrity errors.
**Action:** Always restore the local `trade.qty` to the total original order quantity (`order.q`) upon receiving the final `FILLED` status for an exit order. This ensures that downstream closure logic calculates PnL and fees for the full position size rather than just the final execution fragment.
## 2026-06-30 - Multi-Part SL Execution & Authoritative Fee Integrity
**Learning:** Binance FAPI Stop-Loss orders often execute in multiple slices. Assumptions of atomic fills lead to two critical failures: 1) The Watchdog's "Quantity Parity Audit" detects a mismatch between the remaining position and the original order size during partial fills, triggering redundant and dangerous cancel-replace loops. 2) Local PnL calculation defaults to the final slice's quantity if the total order size is not explicitly restored. Additionally, authoritative commissions (`order.n`) arrive via both REST (entry) and UDS (execution), risking double-counting without Trade ID (`order.t`) deduplication.
**Action:** Implemented "Live-Remaining Sync" where `trade.qty` tracks the exchange's remaining quantity during partial fills, and "Total-Restoration" on final fill before closure. Introduced a `tradeExecutionCache` using Binance Trade IDs to ensure authoritative fee accumulation is idempotent across REST and UDS paths.
## 2026-06-29 - Multi-part SL Fill PnL & Quantity Divergence
**Learning:** The engine previously assumed Stop Loss fills were atomic. In reality, Binance FAPI SL orders can fill in multiple slices. Ignoring `PARTIALLY_FILLED` UDS events caused local quantity divergence and risk calculation errors. Furthermore, using the price of the final slice for the entire trade quantity resulted in PnL inaccuracies.
**Action:** Implemented `PARTIALLY_FILLED` synchronization to track remaining quantity during SL hits. Final `FILLED` events now restore cumulative quantity and prioritize the authoritative `avgPrice` (`ap` field) to ensure PnL precision for multi-part executions.

## 2026-07-04 - Multi-Part Execution Commission Double-Counting
**Learning:** Authoritative commissions from Binance FAPI arrive via the User Data Stream (UDS) 'n' field on every execution slice ('TRADE' events). However, the engine's closure logic (closeTrade) also attempted to estimate and apply a taker fee when a trade transitioned to terminal states. This resulted in double-counting of commissions for all exchange-confirmed fills. Authoritative exchange data must always suppress local estimation.
**Action:** Implemented a 'feesAlreadyAccounted' signal in the 'trade.exchange_close' event. Modified OrderManagerService.closeTrade to bypass fee estimation when this flag is present. Refactored UDS handling to consolidate terminal state detection and authoritative fee accumulation.

## 2026-07-06 - In-Flight Closure Race & State Resurrection
**Learning:** A high-severity race condition occurs when a trade is successfully opened on the exchange but fills its Stop Loss (or is closed via event) before the local engine transitions it from "entering" to "active". If the closure event arrives while the trade is only in the `inFlightEntries` registry, it may be ignored by local Map-based logic. Subsequently, when the entry acknowledgment returns, the engine incorrectly adds the trade as `OPEN`, creating a "ghost position" that is actually closed on the exchange.
**Action:** Implemented "In-Flight Local Map Recovery" in `PositionTrackerService.closeTrade` to search the `inFlightEntries` registry if the primary Map lookup fails. Added a "Terminal Status Guard" in `addTrade` to discard trades that reached a terminal status (e.g., `CLOSED_SL`) while in-flight, preventing the resurrection of closed trades.

## 2026-07-08 - Binance FAPI Parameter Conflict (Error -1106)
**Learning:** Binance USDS-M Futures (FAPI) enforces strict parameter exclusivity for orders. Specifically, if `closePosition: true` is provided in a `STOP_MARKET` order, the `quantity` parameter MUST be omitted. Inclusion of both results in a rejection (Error -1106), even if the quantity matches the actual position size. This caused our fallback Stop-Loss path to fail on accounts where the Algo Order API was unavailable.
**Action:** Modified `OrderManagerService.placeStopLoss` fallback logic to explicitly delete the `quantity` parameter when `closePosition` is set to `true`. Added a regression suite `chronos_sl_compliance.spec.ts` to verify parameter compliance across all fallback paths.

## 2026-07-09 - Authoritative PnL & Ghost Position Prevention
**Learning:** Using Binance FAPI ORDER_TRADE_UPDATE status 'FILLED' as the sole trigger for trade closure risks "ghost positions" when external or partial fills occur. ORDER_TRADE_UPDATE is order-centric, whereas the account position is the final truth. Additionally, local PnL estimation often diverges from the exchange due to multi-part commissions and realized profit (rp) slices arriving via UDS.
**Action:** Implemented "ACCOUNT_UPDATE Authoritative Closure" for external orders - trades only close locally when the symbol's net position reaches zero. Introduced "Incremental Authoritative PnL" where trade.pnl accumulates real-time 'rp' and 'n' fields from UDS slices, synced via delta-based balance updates to prevent double-counting with REST fallbacks.

## 2026-07-10 - Funding Fee & Balance Synchronization Integrity
**Learning:** The engine previously suffered from two compounding synchronization gaps: 1) A race condition where local PnL delta application to 'balanceLive' competed with absolute 'ACCOUNT_UPDATE' wallet balance syncs, leading to double-counting. 2) 'Funding Blindness' where 'FUNDING_FEE' events in 'ACCOUNT_UPDATE' were ignored, causing the session's trade-centric PnL to drift from the actual exchange balance.
**Action:** (1) Deprecated real-time local delta application to 'balanceLive'; 'ACCOUNT_UPDATE' is now the sole authoritative source for absolute wallet balance in live mode. (2) Implemented 'Authoritative Funding Attribution' where 'FUNDING_FEE' events trigger proportionate fee/PnL updates across active trades based on notional value, ensuring session stats stay aligned with the exchange's financial truth.

## 2026-07-11 - Authoritative State Synchronization & In-Flight Abandonment
**Learning:** The engine implemented several "safety guards" that actively sabotaged exchange-state parity: (1) Ignoring quantity decreases in `ACCOUNT_UPDATE` when not locally "closing" created ghost positions if the user manually managed risk on the exchange. (2) Ignoring unrecognized external orders in `ORDER_TRADE_UPDATE` ensured local state never matched exchange reality after manual management. (3) Abandoning trades that failed SL placement/unwind left orphaned, untracked positions.
**Action:** (1) Mandate authoritative sync for all `ACCOUNT_UPDATE` position changes. (2) Implement "Partial Opposite-Side Sync" where unrecognized fills reduce `trade.qty` rather than being ignored. (3) Enforce "In-Flight Recovery" where any successful entry MUST be added to local tracking regardless of subsequent protection failures, ensuring the Watchdog can identify and resolve the orphaning.

## 2026-07-12 - Bot Startup UDS Blind Spot & Event Buffering
**Learning:** A critical "blind spot" exists during bot startup between the initial REST reconciliation (fetching positions/orders) and the establishment of the User Data Stream (UDS). If an order fills or a position changes on the exchange while the bot is reconciling its local state from REST, those events are lost, leading to immediate "ghost positions" or stale price/quantity data.
**Action:** Implemented a "Buffer-then-Reconcile" startup pattern. UDS and event buffering are engaged as the VERY FIRST step of session initialization. Once REST reconciliation is complete and the engine is started, buffered events are replayed to incorporate any exchange activity that occurred during the bootstrap phase.

## 2026-07-13 - In-Flight Entry Promotion & Ghost Position Prevention
**Learning:** Entry orders that fill on the exchange while the local `enter()` REST call is pending (due to network lag or retries) remain in an untracked "in-flight" state. These trades are invisible to the `hotLoop` for exit monitoring and are often incorrectly identified as "ghost positions" by the Watchdog, leading to redundant adoption requests. Furthermore, if the REST call eventually times out, the trade may be abandoned locally while remaining open on the exchange.
**Action:** Implemented "In-Flight Auto-Promotion". Both `ORDER_TRADE_UPDATE` and `ACCOUNT_UPDATE` now match exchange events against the `inFlightEntries` registry and explicitly promote trades to the active list (`positionTracker.addTrade`) upon fill detection. Hardened the `enter()` method with a global `try/finally` block to ensure in-flight status covers the entire retry window.

## 2026-07-14 - Multi-Part Execution PnL Overwrite & Incremental Model
**Learning:** Terminal closure logic (triggered by reconciliation or external events) was performing an absolute PnL calculation from the entry price, assuming the local `trade.qty` represented the entire position. For multi-part executions where some slices were already accounted for via UDS `rp` and `n` fields, this absolute calculation resulted in massive double-counting or overwriting of authoritative data.
**Action:** Transitioned the Live-mode engine to an **Incremental PnL Architecture**. `trade.pnl` is now the authoritative "Net Realized Result so far". All REST entry/exit commissions and manual fee estimates are now subtracted directly from `trade.pnl` (parity with UDS logic). Terminal closure now only adds the profit of the *remaining* quantity to the existing `trade.pnl` balance, ensuring integrity across any combination of tracked and untracked execution slices.

## 2026-07-15 - Liquidation Blind Spot & Multi-Part PnL Double-Counting
**Learning:** Binance FAPI reports liquidations using `executionType: 'CALCULATED'` and `orderType: 'LIQUIDATION'`, which were previously ignored by our UDS handler, leading to "ghost positions". Furthermore, in our Incremental PnL Architecture, restoring `trade.qty` to total size upon receiving the final `FILLED` event causes `closeTrade` to double-count the final slice's profit because it calculates an absolute delta on the full quantity even if the slice was already accounted for via UDS 'rp' fields.
**Action:** (1) Explicitly process 'CALCULATED' execution type as an authoritative closure. (2) Implement an 'alreadyRealized' signal in the EXCHANGE_CLOSE event to suppress redundant PnL recalculation for terminal fills. (3) Defer quantity restoration until the very end of the closure logic to maintain financial precision throughout the execution pipeline.

## 2026-07-17 - Binance FAPI Order Limit Blind Spot
**Learning:** The USDS-M Futures (FAPI) exchange returns distinct order limit headers (`X-FAPI-ORDER-COUNT-10S` and `X-FAPI-ORDER-COUNT-1M`) instead of Spot limit headers (`X-MBX-ORDER-COUNT-10S` and `X-MBX-ORDER-COUNT-1M`). Tracking only Spot headers left the Futures engine blind to Futures order counts, causing order capacity guards to be completely bypassed and risking HTTP 429 bans (Error -1015, TOO_MANY_ORDERS).
**Action:** Always parse both `X-FAPI-ORDER-COUNT-*` and `X-MBX-ORDER-COUNT-*` rate-limiting headers in a case-insensitive manner to ensure proper priority-based throttling and capacity checks for Futures connections.
